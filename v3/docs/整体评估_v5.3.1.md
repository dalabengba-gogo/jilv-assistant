- 日期：2026-10-19 15:56

## 0. 一句话结论

**功能层面已经跨过关卡，问题从"做不成"变成"白费劲"。**

今天修的三件事（域外死循环、介绍页前往、等待超时不计入统计）都是"做不成 → 做成了"的量级；
剩下最值钱的改进不在正确性，而在**效率**和**留痕**：

- 一轮日常 28 分钟里，真正"点一下/滑一下"的时间只有 **6 分钟（21%）**，其余全是 OCR、截图、写死的 sleep 和等待超时；
- 抽掉这三块浪费，同样的逻辑可以跑到 **15 分钟左右**（-45%），这是当前投入产出比最高的一件事；
- 另外每天跑完**结论不留痕**——关掉 GUI 就只剩一份文本日志，多开 5 个号时想知道"昨天谁哪个玩法没做成"只能翻日志。

### P0-1 「若…则…」类步骤系统性漏标，每轮制造 6+ 条假失败

**现象（今日实测）**

```
15:32:57  ⚠ 步骤未做成: [若还有结算弹窗再点一次(1/3)]
15:35:12  ⚠ 步骤未做成: [若还有结算弹窗再点一次(1/3)]
15:37:33  ⚠ 步骤未做成: [若还有结算弹窗再点一次(1/3)]
15:50:35  ⚠ 步骤未做成: [域外-批次后-若面板开着则关闭]
15:53:00  ⚠ 步骤未做成: [域外-批次后-长等前若面板开着则关闭]
15:55:02  ⚠ 步骤未做成: [域外-批次后-若面板开着则关闭]
```

**根因（两层）**

1. `daily_dixia_3x.yaml:384`「若还有结算弹窗再点一次」**有 click 动作**，所以不吃 v5.3.0 的"纯等待超时算软失败"通道（那条规则限定 `not step.action`）；
2. v5.3.1 的批量标注是**手写 targets 列表**（9 个名字），漏了这一类。全项目同类问题还有：地煞结算弹窗、域外"若面板开着则关闭"×3、"长等前若面板开着则关闭"、五环/师门"若弹离线完成提示"（这几条已标）。

**方案（推荐，成本 1 小时）**

- 新增 `scripts/check_optional.py` 进 `check_refs`：静态扫描所有 `name` 含 `若`/`若有`/`如果` 且有 `wait` 的步骤，输出"疑似条件探测但未标 optional"清单，**打印而不报错**，作者逐条确认；确认后的名字写进白名单，下次不再提示。
- 引擎侧加一条更根本的语义：`optional_if: {ocr: 奖励总览}` —— 声明"这个条件不成立时跳过属正常"。比 `optional: true` 精确，也不会把"该点没点上"洗白。
- **不建议**直接把"有 wait 有 click 的超时"全算软失败 —— 那会把"点前往没点上"（今天刚修的 bug）一起洗白。

### P0-2 一条龙续跑判据太宽，可能"假续跑"后白等 45 分钟

**现象**（15:24:03–15:24:22）

```
点任务栏-组队一条开跑   → OCR 未找到「组队一条」
一条-切到任务页签       → 仍未找到
一条-任务栏仍有条目则续跑 → 命中(点击 454,227)  ← 这里
一条-续跑后回监控循环    → 45 次 × 60s 监控
```

**根因**：`daily_team_oneloop.yaml` 的续跑判据是

```yaml
ocr_row: {has: ['/'], not: ['V'], region: [356,150,540,320]}
```

"含斜杠、不含 V"几乎命中**任何一条任务行**（今日主界面第一行是「达成条件后继续主线」，其下还有「招募路人 | 跑环任务 [4/5]」「通关第214章」等）。命中后点击 454,227 —— 那是任务栏某行，不一定是组队一条。

今天恰好"一条龙真的做完了"（上一轮 13:11 已完成），所以没暴露损失；但一旦是"任务栏被主线挤占/页签遮挡"，就会**判成在跑 → 监控 45×60s → 最长白等 45 分钟 → 最后仍做不成**。这与 09-29 凌晨那次误判同源，只是方向相反。

**方案（成本 2 小时）**

1. 续跑判据收紧为"**必须含一条龙专属词**"：
   `ocr_row: {has: [], not: ['V'], any_of: ['域外风情','挖宝封妖','烧法任务','商旅护送','帮派任务'], region: [...]}` —— 需要给 `ocr_row` 加 `any_of`；
2. 点击后加 **8 秒确认**：`wait: {any:[{ocr:回合},{ocr:自动中},{ui:战斗中}]}`，没反应就撤销续跑、按"无一条龙"走收尾；
3. 监控循环的 `max_visits: 45` 降为 20（20 分钟足够覆盖最长一条龙间隔），并让"连续 3 轮既无条目、又无战斗、又无寻路"直接收尾。

### P0-3 找卡步 timeout 8s < 2 帧，失败直接掉进 11 步恢复块

**现象**（15:42:05）

```
点五环任务卡片(OCR定位)  timeout: 8, retry: 1
→ 2 次全败（一轮全图 OCR 1.5~5s，8 秒只够 1~2 帧）
→ goto 五环-恢复-若面板已开则直接找卡
→ 走 11 步恢复块（点页签/两次回顶/队伍判定）约 20 秒
→ 15:42:26 第二次点中（框 299,105 168x43）
```

根因是 v5.1.0 已确认的**世界播报横幅盖住卡名**：横幅只停留 3~6 秒，8 秒窗口内很可能全程被盖。

**方案（成本 30 分钟，只改 YAML）**

```yaml
- name: 点五环任务卡片(OCR定位)
  click: {ocr: 五环任务}
  timeout: 12          # 8 → 12，确保 ≥2 帧
  retry: 1
  on_fail: {goto: 五环-找卡-等横幅再点}   # 不再直接进 11 步恢复块
```

新增中间块（师门同款）：`sleep 4（等横幅滚走）→ 再点一次 → 仍失败才 goto 恢复块`。
今日实测：失败后 20 秒才成功，改完预计 6~8 秒。师门/域外的找卡步同样处理。

### P1-1 手动停止期间的截图异常被记成"真失败"

**现象**（15:17:17）

```
⏹ 收到停止请求, 正在安全停止…
步骤[每日必领-①打开商城] 发生意外异常(DeviceError: 截图失败) → 按失败处理
→ 结束统计: 真失败 1 步
```

**根因**：`runner.py:957` 的 `except Exception` 在 `except InterruptedError` **之前**，停止时 adb 截图失败抛的是 `DeviceError` 不是 `InterruptedError`，于是被当成故障记账。

**方案（成本 15 分钟）**：在该分支开头先判：

```python
if not self.running or self._stop_at:
    self._emit_log("warning", "⏹ 任务已按请求停止(停止期间的异常不计入失败)")
    return False
```

停止是正常操作，不该在统计里留疤——这与 v4.0.1"手动停止不是失败"的界面修正是同一件事的另一半。

### P1-2 队伍申请守卫只进了两个玩法

师门/五环的恢复块里有「申请顶替成为队伍队长 → 点拒绝」的守卫，但**地煞、域外、一条龙**进面板找卡时同样会遇到（那几个玩法的面板是同一个）。

**方案（成本 1.5 小时）**：提升为引擎级钩子 —— 在 `_do_action` 的点击后、或 `_wait_with_until` 每次截图后做一次**低成本可见性检查**（模板而非 OCR，避免每帧增加 1.5s），命中就自动点"拒绝"并记一条 info。写在脚本里每处复制 4 步，维护成本太高。

> 注意：这一步必须用**模板**（固定按钮外观），用 OCR 会吃掉 32% 已经很高的那块预算。

### P1-3 单帧判据的通用化（一条龙 4×60s 的代价）

一条龙"任务栏无条目"用 `4 轮 × 60 秒安静确认`兜住单帧误判（今日 15:25:30–15:29:48，**4 分 18 秒**纯等）。这个模式方向对，但：

- 60 秒间隔是为"跨最长约 3 分钟的赶路间隙"设计的；
- 而在**主界面无战斗**场景下，15 秒间隔 × 4 轮就足够（60 秒已属过度保守）。

**方案（成本 2 小时）**：给引擎加稳定态条件

```yaml
wait:
  stable: {not: {any: [{ocr: 组队一条}, {ocr: 域外风情}]}}
  for: 120          # 条件连续保持 120 秒
  interval: 15      # 每 15 秒看一次
```

内部实现就是"短间隔多帧 + 全部命中才通过"，语义比手写 4 组 sleep+wait 清楚，且可按场景调间隔。一条龙段可从 4 分 18 秒压到 1 分钟左右。

### P2-1 OCR `region` 只是事后过滤，不是裁剪识别 —— 32% 耗时的最大来源

**代码事实**（`runner.py:357`）：

```python
def _ocr_find(self, screen, keyword, region=None):
    boxes = self._ocr_boxes(screen)       # ← 全图识别，1.5~5s
    if region:
        boxes = [b for b in boxes if 中心在 region 内]   # ← 只是过滤
```

即：**不管你要找的字在 4×4 的角落还是全屏，每帧都要付 1.5~5 秒**。而全项目 341 帧/轮，其中相当一部分是"只关心右下角任务栏"或"只关心右侧页签"。

**方案（成本 3~4 小时，收益最大）**

1. `recognition/ocr.py` 的 `recognize(screen, region=None)` 支持先 `crop` 再识别；
2. `_ocr_boxes` 加 region 参数与**分区域缓存**：同一张截图按"全图"和"各 region"分别缓存（现有 `_ocr_cache_screen` 只缓存全图）；
3. 脚本侧把 `click: {ocr: X, region: [...]}`、`ocr_row.region`、`ocr_pair` 都走裁剪路径。

**预估**：任务栏/页签类识别（占一半以上）从 1.5s 降到 0.3~0.5s，全轮 OCR 8.8 分钟 → **约 3 分钟**，整体 28 分钟 → **22 分钟**。

**风险**：裁剪区域切到文字边缘会导致识别失败 —— 必须给 region 外扩 10~15px 安全边，且"裁剪未命中时回落全图"一次（只在新脚本/改了 region 时触发）。

### P2-2 截图无跨步复用（417 次 / 28 分钟）

`_grab()` 每次都 `adb screencap`（≈0.79s）。而实测存在大量"上一步刚截完，下一步 0.3 秒内又要截"的连续识别步（如"点页签 → 停顿 1s → 找卡"）。

**方案（成本 1 小时）**：`_grab()` 加 400ms 的**软缓存**（`if now - last_shot < 0.4 and no_action_since: return last_screen`）。点击/滑动后必须强制失效（`_do_action` 里置 `_shot_dirty = True`）。

**预估**：417 次 → 300 次左右，省约 1.5 分钟/轮。收益不如 P2-1 大，但改动极小。

### P2-3 写死 sleep 占 24%，其中大半可换成 wait

73 个 sleep 步 / 6.5 分钟。典型是"点完页签 sleep 1 再找卡"、"滑完 sleep 1 再看"、"点前往 sleep 3 等寻路"。

**方案（成本 2 小时）**

- 写一个 `scripts/audit_sleep.py`：找出"`sleep: N` 紧跟着一个 `wait:`"的相邻对，建议合并为 `wait: {cond, timeout: N}`；
- 全部 `sleep: 1` 的"停顿"步改为 `wait: {not: <上一步造成的过渡态>, timeout: 1}` —— 条件一消失就走，平均省 0.5s/处；
- **保留**这几个安全窗口不动：一条龙"监控-安静确认"、地煞"等12秒"（游戏强制 10 秒后才能点）、各玩法的"等战斗"。

**预估**：6.5 分钟 → 3 分钟，省 3.5 分钟/轮。

### P2-4 等待轮询间隔固定 1.0s

`poll_interval: 1.0` 是全局值。对"等战斗结束（几分钟）"这种场景，1 秒一轮 = 每轮都要截图 + OCR，白白消耗；对"点完按钮等弹窗"又稍慢。

**方案（成本 1 小时）**：支持按步覆盖 `poll_interval`（默认仍 1.0），长等待步写 3~5 秒。粗估省 1~2 分钟/轮，同时降低 adb 压力（多开 5 个号时这条更重要）。

### P3-1 结论不留痕：跑完就只剩文本日志

**现状**：一轮 1022 步 28 分钟，权威结论（5 个玩法 ✔/✘ + 步数 + 失败明细）只存在于 `run_<port>.log` 的几百行文本里；GUI 一关就没了，跨天对比只能人工翻日志。多开 5 个号时，"昨天晚上谁哪个玩法没做成"是个真实且每天都会问的问题。

**方案（成本 4 小时，含 GUI）**

1. 引擎在 `_finish()` 落一份 `logs/reports/2026-10-19_p16416.json`：

```json
{"date":"2026-10-19","port":16416,"account":"账号2","task":"daily_all",
 "start":"15:20:56","end":"15:52:10","elapsed_s":1874,
 "subtasks":[{"name":"五环","steps":100,"verified":true,"failed":0},
             {"name":"域外风情","steps":162,"verified":false,"failed":2}],
 "stats":{"failed":2,"skipped":15,"required_failed":0},
 "failed_steps":[{"index":940,"name":"...","reason":"..."}]}
```

2. GUI 加「运行历史」页签：表格（日期 / 账号 / 玩法 / ✔✘ / 耗时 / 失败数），支持按天筛选、导出 CSV；
3. 保留 30 天，随日志轮转一起清。

这一步的价值：把"以游戏面板为准"这个已经做对的权威判定**沉淀成可比较的数据**，而不是每次重新读日志。

### P3-2 结束通报口径还能再收敛

现在结束横幅是：`⚠ 任务跑完但有 2 步未做成（另有 15 步条件未命中, 属正常）`。
用户看到的第一反应仍然是"是不是漏了"（今天已经因此提过一次）。

**方案（成本 1 小时）**：结束横幅只报**玩法级结论**：

```
✔ 每日日常完成 4/5   ✘ 域外风情 0/50
（细节见 运行历史 / run_16416.log）
```

真失败 = 0 时不出现 ⚠ 字样；有失败时把"哪个玩法"直接点名，而不是"N 步"。步数是排障用的，不是给用户看的。

### P3-3 没有"变慢/卡顿"的观测

崩溃有三件套（`last_action` / `modules` / `threads`），但没有性能指标。今天 13:11 那轮"域外重开面板 10 次把 OCR 压到崩溃"，事前没有任何预警。

### P4-1 dist 已 24 个包 / 7.93 GB

`build_portable.py` 早就支持 `--keep N`（零删除，旧包只改名移到 `_old_*`），但一直没跑过。

**方案**：`python tools/build_portable.py --keep 3`，回收约 6.9 GB。建议每次发版默认带 `--keep 3`。

### P4-2 两个巨型文件

`main_window.py` 1692 行、`runner.py` 1516 行。v3.6.0 已经把渲染拆成 mixin，`runner.py` 的 `run_step` + `_do_action` 仍有约 600 行、承担 8 种职责（等待/动作/记账/跳转/重试/预算/截图/异常分类）。

**方案（不急）**：下次要动 `_do_action` 时顺手拆出 `engine/actions.py`（点击/滑动/jump/sleep/win 通道）与 `engine/accounting.py`（失败记账/验收标记/汇总）。**不为了拆而拆** —— 现在 29 个测试在罩着，拆错了会大面积回归。

### P4-3 没有真机回归，全靠"跑一轮看日志"

今天三个 bug（前往坐标、组队前置、横幅遮挡）没有一个是单元测试能发现的。但每次真机验证要 26 分钟起。

**方案（成本 3 小时，收益长期）**：用 `logs/debug_*/` 已有的**124 张失败现场截图**建一个离线回放集：

```
scripts/e2e_replay.py
  fixtures/                 # 截图 + 期望结论的 json
    shimen_banner_cover.jpg → {"cond": {"ocr":"师门任务"}, "expect": false}
    panel_done_wuhuan.jpg   → {"cond": {"ocr_pair":["已完成","五环任务"],...}, "expect": true}
```

断言"给定这张图，引擎的判定必须是 X"。不需要设备、秒级、可进 CI。模板/阈值/几何门槛这类改动（v5.1.0 那种）以后能靠它守住。

### P4-4 版本号四处同步仍靠手工

`common.py` / `__init__.py` / `README.md` / `使用说明.txt` 四处靠 Edit + 人工核对。今天连着三个版本，全靠仔细。

**方案（成本 1 小时）**：`tools/bump.py 5.4.0 "改动摘要"` —— 一次改四处 + 校验 BOM/CRLF + 打印 diff 供确认。`build_portable.py` 已有四处一致性自检，配套补齐输入端即可。

### P4-5 账号配置与实际设备不校验

`accounts.json` 里 5 个账号全部 `enabled: true`，但 `adb devices` 只有 `127.0.0.1:16416` 一台在线。多开时会 4 个号连不上（状态灯会灰掉，但用户在按下"全部启动"之前不知道）。

**方案（成本 1 小时）**：多开启动前做一次端口预检（`probe_ports` 已有），把"配置了但连不上"的账号先在确认弹窗里列出来，让用户选择"只跑在线的"或"照常启动"。

## 3. 建议的版本节奏

| 版本 | 内容 | 预期效果 |
|---|---|---|
| **v5.4.0** | P0-1 / P0-2 / P0-3 + P1-1 + P1-4 | 每日统计归零；堵住"假续跑白等 45 分钟"；找卡不再掉进 20 秒恢复块 |
| **v5.5.0** | P2-1 / P2-2 / P2-3 / P2-4 | 单轮 28 分钟 → **15~18 分钟**（这是体感最明显的一版） |
| **v5.6.0** | P3-1 / P3-2 + P1-2 / P1-3 | 有"运行历史"可翻；结束只说玩法结论；队伍守卫全局化 |
| **v5.7.0** | P4-3 / P4-4 + P4-1 | 离线回放集兜住识别类回归；发版一条命令；dist 瘦身 |
| 随时 | P4-2 / P4-5 / P3-3 | 顺手做，不单独立版本 |

**建议先做 v5.5.0 的性能三件套**（P2-1 OCR 裁剪 + P2-2 截图缓存 + P2-3 sleep→wait）。
理由：它不改变任何业务判定（29 个测试 + 现有逻辑全部不变），风险最低，但把每天 5 个号的等待时间砍掉近一半 —— 用户感知最强。

## 4. 不建议做的事（避免过度工程）

| 想法 | 为什么不做 |
|---|---|
| 上 YOLO / 目标检测替代模板+OCR | 现有识别在 540×960 固定分辨率下够用；引入模型会让 runtime 从 337MB 再涨、启动更慢、跨机器一致性变差 |
| 把每个玩法改写成 Python 代码 | YAML + 引擎已经能表达全部需求（条件、循环、跳转、验收），改代码只会让"改一个坐标要重新打包"变回现实 |
| 多机 / 云端调度 | 当前是单机 5 开，规模不够；`accounts.json` + 端口绑定已经够用 |
| 给"条件未命中"做更细的分类 | 已经分到 `skipped_steps`，再细分对用户没有增量信息（P0-1 要修的是"该软的没软"，不是分类粒度） |
| 大改 GUI 布局 | 现有 6 页签 + 左侧控制是合理的；P3-1 加一个页签即可，别重排 |
