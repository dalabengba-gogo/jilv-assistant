# v4.1.0 现存问题与改进方案（2026-10-18）

> 本文**只提方案，不改代码**。所有结论都带 `文件:行号` 证据，来自对 v4.1.0 源码的实读。
> 严重度 = 对「跑得对 / 跑得稳 / 看得清」三件事的影响程度，不是代码质量评分。

## 一句话结论

**能跑、也基本跑得对，但有两处还在骗自己**：① 面板没挂「已完成」徽标时，通报仍然是「任务成功 ✔」（验收失败被当成条件未命中）；② 子进程只要没被正常收尾，界面就永远显示「运行中」（只有 pid 判活、没有心跳）。
其余是**日志会撑爆磁盘、定时任务错过即丢、产物被就地运行污染**这三件迟早要还的账。

其中「磁盘与体积」已按用户要求（2026-10-18）立为两个专项，附实测数据：
- **专项 A（绿色版结构与空间占用）**：关键发现是 `dist` 3.4GB 里 **88% 是 9 份重复的
  runtime** —— 共享一份 + 只留最近 N 个包即可回收约 2.7GB，比"裁剪单个包"划算一个量级。
- **专项 B（运行日志定期清理）**：现有滚动只在跑任务时触发，且 200 张未压缩 PNG 的配额
  单目录就能稳到 170MB；实测两天 235MB。需补触发点 + 降配额 + JPEG 化三管齐下。

## P0 — 直接影响"做成没有"的判断（建议第一批改）

### P0-1 验收点判失败时，被当成"条件未命中"，界面永远不显示 ✘ ★最严重
- 现象：面板明确没有「已完成」徽标，通报仍是「任务成功 ✔」。
- 证据：`engine/runner.py:863`（`_is_optional` 为真即计入 skipped，不进 failed）；
  实测 `assets/tasks/parts/daily_wuhuan.yaml:254-260`、`266-271` 两个 `verify_done` 步
  都走了 optional 分支；随后 `runner.py:1163` 的 `if self.failed_steps:` 判假 →
  `runner.py:1174-1177` 只输出「✔ 任务完成」；GUI 侧 `gui/main_window.py:2433-2435`
  成功分支同样只报"最后执行到哪一步"。
- 影响：用户确立了"以游戏面板为准"，但面板说没做成时，界面给出的答案仍然是"成了"。
  这是**当前版本最严重的问题**——权威答案被静默丢弃。
- 改法：
  1. `verify_done` 步骤强制不走 optional 分支（在 `_is_optional()` 里短路返回 False）；
  2. `verified is False` 时计入失败通道（至少是子任务级 ✘），不要靠"掉了几步"反推；
  3. GUI 成功路径也要渲染**有验收点的子任务行**（现在成功一律不渲染子任务行），
     让用户一眼看到 ✔/✘；"最后执行到第 N 步"降为副标题。

### P0-2 验收点只覆盖了 2/7 个玩法，其余仍靠数"掉了几步"
- 证据：`verify_done` 全工程仅 4 处 —— `daily_shimen.yaml:297,310` 与
  `daily_wuhuan.yaml:258,270`；`daily_claim` / `daily_dixia_3x` / `daily_team_oneloop` /
  `daily_yuwai` / `daily_pure_mode` 全部为 0（7 个 parts 里只有 2 个接了）。
- 可复用的 **10 步**收尾块：`daily_wuhuan.yaml:231-277`（开面板 → 等面板 → 点日常页签 →
  回顶 → 停顿 → `ocr_pair:[已完成,卡名] pair_min_score:0.75 verify_done` → 停 3 秒 →
  复核 → 关面板兜底 → 等回主界面）。
- 卡名已确认：`师门任务` / `五环任务` / `域外风情·修罗任务·抓鬼任务` / `挑战地煞`；
  「每日必领」没有独立卡片，判据应取"面板上不再有待领宝箱"。
- **域外风情没有徽标**（显示"今日额外次数 0/50"）的候选判据与代价：

  | 方案 | 判据 | 代价 |
  |---|---|---|
  | a 任务栏行判别（推荐） | `has:[域外风情] not:[V/✓]` | 只在主界面可见；需先取样确认是挂 V 还是变灰 |
  | b 介绍页 `50/50` | 已在 `daily_yuwai.yaml:171-176,336-341` 使用 | 每次判定多"点卡片→等任务说明"，约 +10s |
  | c 卡片灰度模板 | 注册表已标 dynamic | 65 个模板全无 alpha 通道，掩膜机制从未生效，稳定性差，不建议 |
  | d OCR 解析"x/50" | 需新能力 | 引擎现在只能做包含/排除，且面板数值不实时刷新 |

  **建议 a+b 组合**（a 命中即成；a 不可用时退回 b 一票通过）。
- 必加兜底：`daily_yuwai.yaml:398` 是一条 `jump: 域外-批次结束后重开面板` 的无出口回边，
  而 `jump` 不计入 goto 死循环保护（`runner.py:1131` 只统计 `cause=="fail"`）
  → 没有徽标就可能无限批次。改法：批次上限 N 轮，超 N 轮强制 `verified=False` 收尾。

### P0-3 假运行：只有 pid 判活、没有心跳；孤儿通道会被认成"运行中"
- 证据：`live.py:246-282 is_active()` 只查 PID 存活；`scripts/run_one.py` 无任务级超时、
  无看门狗；`gui/main_window.py:2488-2502 _discover_ports` 在 `rd.new_run`（live.py:218，
  通道 meta 的 rid 变化）时 `store.reset()` 成 running。
- 影响：子进程 adb 卡死（活着但不产出）、或 pid 被系统复用给别的进程时，
  界面永远「运行中」，定时/重复启动被拒——**这正是昨天手动停止卡住的同族问题**。
- **【2026-10-18 复核修订】** 本条只剩"无心跳"这一半：
  ① PID 误判那半已在 **v4.1.0 修掉**（`is_active()` 改成 `OpenProcess` +
  `GetExitCodeProcess`，退出码 ≠ 259 才算真死），原措辞"只查 PID 存活"已过时；
  ② "目录存在就 reset 成 running"也不准确 —— 触发条件是 `rd.new_run`，
  且 `:2531-2538` 已有 `if not rd.is_active(): mark_stopped` 兜底。
  真正剩下的风险只有：**PID 活着但卡死**（adb 挂住、进程假死）这一种。
- 改法：
  1. meta 增加心跳时间戳，reader 端超过 60~120s 无新事件/新帧即判死；
  2. `run_one.py` 加 `--max-run-seconds` 任务级超时；
  3. GUI 重启认回孤儿通道时，先比对 meta 的启动时刻，超过阈值（如 2 小时）只标
     「未知/已结束」，不要 reset 成 running。

### P0-4 日志不滚动、不落关键排障信息，磁盘会撑满
- 证据：`common.py:551,562` 用 `%H:%M:%S` + 裸 `FileHandler` 追加（无日期、无滚动）；
  `scripts/run_one.py:44,51` 与 `gui/multi_panel.py:253` **对同一文件开两个句柄**；
  `engine/runner.py:954,957` 失败截图用未压缩 PNG（`.png` 文件名 / `cv2.imencode(".png")`），
  单张实测 **853KB**；滚动只覆盖 debug 截图（`config.yaml:47-48`：200 张/7 天，
  且只在跑任务时触发）。
- 实测体积：`v3/app/xyfz_auto/logs` 已 **159MB**，`dist/鸡驴助手_v4.1.0` 内 **235MB**；
  6 个目录（本机+5 子）理论峰值 ≈ **850MB**。
- 更糟的是**分数永远不落盘**：`runner.py:339` 命中分数是 debug 级，而 logger 级别是 INFO
  → "模板被角标污染导致 0.79 卡在 0.80 阈值下"这种高频故障，日志里只剩"识别失败"，
  看不出差多少；步骤完成行也没有耗时（`runner.py:673`）。
- 改法：文本日志换 `RotatingFileHandler`(5MB×3)、格式加 `%Y-%m-%d`；
  步骤完成加 `(12.3s)`、命中提到 info 并带 `score=0.83(阈值0.80)`；
  行首加 `[port][run]` 前缀；失败截图改 JPEG q=80（853KB→约 60KB）；
  启动时做一次 logs 总量自检并提示。
- **本条只解决"写什么、写多大"；"定期清理旧日志"单列为专项 B（见下）。**

### P0-5 定时任务：错过即永久丢失、失败也消耗当天份额、状态只存内存
- 证据：`gui/main_window.py:2056-2059` 超过到点 3 分钟直接置 `today` 后 `continue`
  （**无任何日志与提示**）；`:2081` 先置 `today` 再启动 → 设备未连（`:2119-2122`）、
  脚本找不到（`:2091-2093`）时当天份额照样消耗且**不重试**；
  `_timer_runs` 是内存 dict（`:2054`）不落盘 → GUI 崩溃后重启会**重复触发**；
  `:2062` 定时路径**没有错峰**（错峰只存在于手动「启动全部」`multi_panel.py:315-321`）。
- 影响：机器关机/休眠/没开 GUI，这天 5 个号的日常静默蒸发；反之崩溃重启会跑两遍。
- 改法：`_timer_runs` 持久化（带日期）；错过时记一条「[定时] 错过 HH:mm，今日不补跑」
  并提供可选补跑开关；启动失败不消耗份额、改 5~10 分钟退避重试 N 次；
  定时路径复用 per-account 错峰。

## P1 — 稳定性与工程卫生

### P1-1 UI 回调异常兜底只覆盖了 14 处调用点
- 证据：全工程 `_safe_call` 命中 16 处，其中 1 处是定义（`main_window.py:64`）、
  1 处是注释（`common.py:191`），**真正调用点只有 14 处**。未包裹的有
  `multi_panel.py:40 _poll_procs`、`main_window.py:682/685`（启动/停止）、
  `main_window.py:290-306`（全部菜单）、`main_window.py:492`（托盘双击）、
  以及几乎所有 `clicked.connect`。
- 影响：pythonw 下槽内异常回溯被丢弃，表现就是"点一下按钮程序没了"；
  `_poll_procs` 一崩，整个多开状态机停摆。
- 改法：统一 `guard(slot)` 包裹所有 `connect`；给 `_safe_call` 加限流
  （250ms 定时器异常会以 4 条/秒灌 `crash.log`，该文件无大小上限）。

### P1-2 渲染不看页签可见性，且每帧多次全幅像素拷贝
- 证据：`render_mixin.py:46-51` 无条件跑日志/画面/步骤；`:230-231` 一次 tick 内
  `store.channels()` 调两次；`live_panel.py:97-111` 缩略图经
  `bgr_to_qimage`（`screen_view.py:15-19`，两份全幅拷贝）+ `scaled`，
  选中时 `:279` 再转一遍；`main_window.py:1218` 每 tick 对每盏灯无条件 `setToolTip`。
- 量级：5 个号同时出帧时，每秒约 25~40 次全幅拷贝（540×960≈1.55MB/份），
  主线程约 10~20% 占用在做纯搬运。
- 改法：按可见页分流（不在画面页就不转码）；缩略图按 (port, frame_seq) 去重并降到
  2~3fps；去掉多余的 `.copy()`；文本/tooltip 先比对再写。

### P1-3 单步预算没启用，判定类步骤只识别一帧
- 证据：`config.yaml:41` 的 `max_step_seconds` 被注释掉 → `runner.py:437` 默认 0；
  `daily_yuwai.yaml:219,372` 是 `timeout:5400 retry:1`，单步最坏 10800s（3 小时）；
  而 `daily_yuwai.yaml:52,98,105…` 的徽标/面板判定是 `timeout:3~5 + retry:0`
  → 单轮约 6s（`runner.py:301-303` 自述），实际**只看了一帧就放弃**。
  `Step.verify`（`model.py:29`）在**生产脚本里 0 次使用**（点击后不校验效果）。
  【2026-10-18 复核修订】原写"946 步"无法复现：生产脚本 `- name:` 约 550 条
  （含 tests 608 条，loop 展开后约 1 千步）；且 tests 目录下另有 8 处 `verify:`，
  "0 次"仅在**生产脚本**口径下成立。
- 改法：开启分级 `max_step_seconds`（全局 1800，长战斗步用新增 `step.max_seconds` 单独放宽）；
  判定类步骤 timeout ≥ 2×单轮成本、retry ≥ 1；启用 `verify`；补整任务/整段 deadline。

### P1-4 硬杀子进程，收尾缺位
- 证据：`multi_panel.py:341-346,355` 直接 `p.terminate()`（Windows 即 TerminateProcess）；
  `run_one.py:109` 取锁、`:191` 释放锁只在正常路径尾，**无 try/finally、无 atexit**，
  也不补写 `task_end`。
- 改法：`run_one.py` 用 try/finally + atexit 释放锁并补 `task_end`；
  先发优雅停止信号，超时再 TerminateProcess。

### P1-5 本机端口与多开端口相同时状态串号 + 句柄永不回收
- 证据：`multi_panel.py:302-314` 只在 GUI 正忙时跳过与本机同端口的账号；
  `main_window.py:2458-2461` 对本机端口也会建 LiveReader 且 `source="child"`，
  而 `:2544` 回收时 `port != self._local_port` 把它排除 → **永不回收**；
  `:1796-1799` 停止按钮此时也点不动。
- 改法：launch 时禁止 `port == local_port`，或建立统一的"端口所有权"表。

### P1-6 诊断包整读大日志，且缺定时/磁盘/adb 原文
- 证据：`diagnostics.py:75-84` 用 `f.readlines()` 全量读入（run.log 到几百 MB 时吃 GB 级内存）；
  导出内容仅 01~08，不含定时清单、磁盘剩余、日志体积、`adb devices` 原文。
- 改法：双端 deque 尾读；补 `09_定时任务.txt` / `10_磁盘与日志体积.txt` / adb 原文。

### P1-7 dist 堆积 3.4GB，产物被"就地运行"弄脏
- 证据：`dist/` 下 9 个版本 ≈ **3.4GB**（都是 10-17~18 一天内产生的）；
  v4.1.0 包内混入 **235MB logs** + `gui_settings.json` + `gui_timer.json`。
  两类要分开看：`build_portable.py:148-150` 的 gui_settings/gui_timer 是**进 errs
  会阻断**（打包规则本该排除它们，出现即逻辑出错）；`:151-156` 的
  accounts.json / logs / _collect 才是只 `print` 警告**不阻断**。
- 补充实测：打包规则**已经**排除了 logs（`build_portable.py:44`，`EXCLUDE_DIRS`
  含 `logs`），包里那 235MB 是**在 dist 里就地运行**长出来的 —— 所以真正的解法
  不是"再排除一次"，而是**产物目录与运行目录分离 + 定期清理**（见专项 A、专项 B）。
- 改法：见**专项 A**（共享 runtime / `--keep N` / runtime 裁剪 / 运行目录分离）。

### P1-8 版本号"第四处"只校验了 2 处，第五处已实际过期
- 证据：`build_portable.py:166-169`（版本校验块 162-178）只校验 `__init__.py` 与 `使用说明.txt`；
  `app/xyfz_auto/README.md:5` 至今仍写 **v3.9.0**（实际 4.1.0）。
- 改法：校验清单加上两个 README，或合并成一份由 `APP_VERSION` 生成。

## 专项 A — 绿色版结构与空间占用（2026-10-18 立项）

> 用户指定列入计划。目标：**结构合理化 + 降低占用**。下面体积全部实测自
> `dist/鸡驴助手_v4.1.0`（`du -sh`，2026-10-18 09:5x）。

### A-0 实测基线

| 层 | 体积 | 构成 |
|---|---|---|
| `dist/` 总计 | **3.4 GB** | 9 个版本目录，全部 10-17~18 内产生 |
| 单包 v4.1.0 | 581 MB | `app` 244M + `runtime` 337M |
| `app/xyfz_auto/logs` | **235 MB** | 就地运行产物（打包已排除，跑一次就长回来） |
| `app` 实际代码 | **约 9 MB** | gui 686K + engine 270K + assets 1.3M + tools/adb 6.6M |
| `runtime` | 337 MB | `Lib` 314M、`DLLs` 14M、`include+libs` 2.9M |
| `runtime/Lib/site-packages` 前六 | — | cv2 113M、PySide6 60M、onnxruntime 33M、numpy 24M+`numpy.libs` 21M、PIL 15M、rapidocr 14M |

**关键判断：真正的大头不是"一个包多大"，而是 dist 里躺着 9 份一模一样的 runtime
（9 × 337M ≈ 3.0GB，占 dist 的 88%）。** 把单个包从 337M 裁到 290M 只省 47M×9=0.4GB，
而"共享一份 runtime + 只留最近 3 个包"一步就能省 2.7GB。所以**先做结构，再做裁剪**。

### A-1 ★ 共享 runtime（收益最大、风险低、不占版本号）

- 做法：`dist/_runtime_shared/3.13.12/` 只放唯一一份解释器与各依赖；各版本包内的
  `runtime` 改成 **junction** 指向它（Windows `mklink /J`，普通权限即可建，同盘有效）。
- **对现有代码零改动**：两个启动 bat 都用 `%~dp0runtime\pythonw.exe`，junction 对此透明。
- 风险与兜底：
  1. junction 不跨盘、复制目录时目标不跟随 → 构建脚本提供两个模式：
     `--link-runtime`（默认，本机开发用）／`--copy-runtime`（外发前固化成实体目录）；
  2. `validate()` 增加"runtime 可解析且 `pythonw.exe` 存在"自检，链接断了要报错而不是
     让用户双击 bat 后没反应；
  3. 手工删 `dist/_runtime_shared` 会让所有旧包一起失效 → 在同级放一个 `README.txt`
     说明，且 `--keep` 清理时永不删该目录。
- 收益：**3.4GB → 约 0.6GB**。

### A-2 旧包裁剪与"产物/运行目录分离"

- `build_portable.py --keep N`（默认 3）：打包完成后自动删除更早的版本目录。
  安全约束三条：
  1. 删前打印清单（路径 + 体积 + 最后修改时间），需 `--yes` 显式确认，绝不静默删；
  2. **跳过正在运行的包** —— 检查是否有 `pythonw.exe` 的进程路径落在该目录下
     （前面踩过 mutex 与"杀旧进程"的坑，这里同理），占用则跳过并提示；
  3. 即便如此也建议先进回收站而不是硬删（dist 是自己产物，风险可控，但仍留退路）。
- 清理旧包内 logs：旧包的 logs 基本都是陈年截图，清掉即可回收约 1GB，
  与 `--keep` 合并为一步「打包后卫生」。
- **产物/运行目录分离**（治本）：把要长期跑的包从 dist 里拷出去（如
  `D:\鸡驴助手_运行\`），dist 只当干净母版。启动 bat 检测到自身位于
  `...\dist\` 下时，在系统日志提示一次"建议拷出 dist 再长期运行"，不阻断。

### A-3 runtime 裁剪（单包 337M → 约 288M，−14%）

## 专项 B — 运行日志定期清理（2026-10-18 立项）

> 与 P0-4 同源，但分工明确：**P0-4 管"写什么、写多大"（格式/分数/耗时/压缩），
> 专项 B 管"旧的东西怎么清掉、什么时候清"。**

### B-0 现状实测（v4.1.0/logs，两天内）

| 对象 | 现有策略 | 实测 |
|---|---|---|
| `logs/debug`（本机） | `rotate_files`：200 张 / 7 天，**只在跑任务时触发** | **92M** |
| `logs/debug_16416` | 同上 | **87M** |
| `logs/debug_16512/16384/16480/16448` | 同上 | 19M / 14M / 13M / 12M |
| `logs/run.log`、`run_<port>.log` | 裸 `FileHandler` 无限追加，无日期、无滚动 | 256K / 156K / ~30K×4 |
| `logs/live/port_*` | **全工程无人清理** | 790K（量小但孤儿目录只增不减） |
| `logs/crash.log` | 无上限（限流缺失时 4 条/秒灌） | 0 |
| **合计** | 无总量闸门 | **235MB / 2 天**；6 个目录理论峰值 ≈ 850MB |

**为什么现在没兜住**（两条，都得改）：

1. **触发点太少**：`rotate_files` 全工程只在 `engine/runner.py:941` 调过一次，
   也就是**只有跑任务时才清**。不跑的那些天只进不出。
2. **配额本身就定大了**：`config.yaml:47-48` 是 `debug_keep_max: 200` 张 / 7 天，
   而失败截图是**未压缩 PNG，实测单张 853KB** → 单目录稳态上限就有
   **200 × ~450KB（均值）≈ 90MB，最坏 170MB**；6 个端口目录理论峰值 **≈ 1GB**。
   实测 92M / 87M 恰好落在这个区间 —— 滚动其实"生效了"，只是天花板太高。

**所以必须两条一起改**：触发点补齐（B-1 第 2 条）+ 配额与单张体积双降。
按 P0-4 把失败截图改 JPEG q=80（853KB → 约 60KB）后，同样的 200 张只剩 **约 12MB/目录**，
6 个目录 ≈ 72MB；再把 `keep_max` 收到 120，稳态约 **7MB/目录、合计 42MB**。

### B-1 机制设计

1. **统一配置段**（`config.yaml` 新增，只管文本与总量；截图沿用已有的
   `engine.debug_keep_max/keep_days`，**不新开第二处截图配置**，免得两边打架）：
   ```yaml
   log_retention:
     auto_clean: true      # 总开关
     text_max_mb: 5        # 单份文本日志上限
     text_backups: 3       # 轮转份数 → run.log 等最多 20MB/份
     quota_mb: 500         # logs 目录总量闸门
   ```
   建议同时把 `engine.debug_keep_max` 从 200 收到 **120**（配合 JPEG 化，
   稳态约 7MB/目录）；`keep_days` 7 天保持不变。
2. **三个触发点**（现有只有一个，必须补齐前两个）：
   - **启动时自检一次**（现在完全没有 → 隔几天没跑，logs 就默默涨）；
   - **每天首次跨日**（复用已有的日切判断）执行一次；
   - **每次任务结束后**（debug 滚动已在此，补齐文本与 live 清理）。
3. **清理顺序**（超配额时"最旧先删"，且绝不删正在写的文件）：
   `debug*` 截图（按 mtime）→ 已结束端口的 `live/port_*`（>24h 无更新）
   → 文本日志轮转备份 → 仍超配额则在系统日志告警并提示手动处理。
4. **文本日志滚动**：换 `RotatingFileHandler(5MB×3)`，格式加 `%Y-%m-%d`。
   ⚠ **前置依赖**：`scripts/run_one.py:44,51` 与 `gui/multi_panel.py:253` 对同一个
   `run_<port>.log` 开了**两个句柄**，直接改轮转会两边打架（一个在写、一个在切）。
   必须先把子进程日志收敛成单一写入方（子进程自己写、父进程只读），再上轮转。
   这条与 P0-4 是同一处改动，**必须一起做**。
5. **GUI 入口**：「运行控制」区加「清理日志」按钮（下拉：清 7 天前 / 清空全部日志），
   执行前弹确认并显示"将释放 X MB、涉及 N 个文件"；每次清理在系统日志留一行结果。
   自动清理也走同一套函数，行为一致、便于排查。
6. **外发前清理.bat**：补上 `shots/` 与 `_collect/`（见 P2 末条），并顺带清 logs。

### B-2 约束（别清出问题）

- **绝不删正在跑的端口目录**：清理前先取当前活动端口集合，命中即跳过。
- 失败截图保留 ≥14 天：识别分数、失败现场全靠它，删了就只能等下次复现。
- 不可撤销 → 清理前在系统日志打印前 20 条待删清单与总量，让用户事后能核对。
- 清理动作放在**后台线程**（`_run_bg`），别因为扫几万个文件把界面卡住。
